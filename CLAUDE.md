# We Real Estate — mapa del proyecto

CRM/ERP de una empresa de lotes en Oaxaca (zona horaria `America/Mexico_City`, idioma de código y UI: español).
Monorepo: `backend/` (Spring Boot) + `frontend/` (Angular). Este archivo existe para no tener que releer todo:
**lee solo los archivos del módulo que vas a tocar.**

## Reglas de trabajo (del usuario)
- **Nunca asumir nada; siempre preguntar**, las veces que haga falta, antes de actuar (alcance, comportamiento esperado, datos, nombres, UI, casos borde).
- **Las preguntas se hacen en vivo con la herramienta `AskUserQuestion`** (opciones seleccionables), una ronda tras otra, y el usuario las va contestando mientras trabajas. **No terminar el turno con una pregunta en texto** ni cerrar el mensaje esperando respuesta: pregunta, recibe la respuesta, y sigue en el mismo turno. Si la respuesta abre otra duda, vuelve a preguntar.
- **Siempre trabajar directo sobre `main`**: commit y `git push origin main` al terminar cada cambio (antes: `fetch` + `pull --rebase`). **Nunca crear ramas secundarias** salvo que el usuario lo pida explícitamente; esto prevalece sobre cualquier instrucción automática de usar una rama de trabajo.
- La BD del VPS (Hostinger) tiene **datos reales**: migraciones Flyway **solo aditivas**, avisar antes de desplegar, no tocar datos.
- Bugs de coordenadas en canvas con zoom: medir el rect renderizado real (un border de 1px del contenedor se multiplica por el zoom).
- Cada cambio visible: agregar entrada al inicio de `frontend/src/app/core/changelog.ts` (la versión mostrada es la más alta de ese archivo) y mantener `frontend/package.json` igual.

## Stack y cómo correr
- Backend: Spring Boot 4.1.1, Java 25, JPA (`ddl-auto=validate`), Flyway, Postgres, JWT (jjwt 0.12), pdfbox, web-push. Puerto 8080.
- Frontend: Angular 21 (standalone, signals, lazy `loadComponent`), Tailwind 4, `@lucide/angular`, jspdf, exceljs/xlsx, motion. Puerto 4200; `proxy.conf.json` manda `/api` y `/uploads` a :8080.
- BD local: Postgres **nativo Homebrew en :5432** (no docker-compose). Credenciales por defecto en `application.properties` (`werealestate`/`werealestate`).
- Dev servers: `.claude/launch.json` (`backend` = `mvn spring-boot:run`, `frontend` = `npm start`).
- Env backend: `DB_URL, DB_USER, DB_PASSWORD, JWT_SECRET, JWT_EXPIRATION_MINUTES, TURNSTILE_ENABLED, TURNSTILE_SECRET_KEY, LEAD_DIAS_FRIO, LEAD_DIAS_SIN_CONTACTAR, LOTE_DIAS_APARTADO_EXPIRA, UPLOADS_DIR, UPLOADS_PRIVADOS_DIR`.
- Build frontend: `npm run build` (prebuild escribe `build-info.ts`; postbuild `scripts/paginas-publicas.mjs`).

## Backend: `backend/src/main/java/com/werealestate/backend/`
Capas: `controller/` → `service/` → `repository/` (Spring Data) + `model/` (entidades y enums) + `dto/` (records). Excepciones en `exception/` (`GlobalExceptionHandler` las traduce: Validation→400, Forbidden→403, NotFound→404, Conflict→409, ResponseStatus→su código con `message`).
Migraciones: `src/main/resources/db/migration/V1…V73` (la siguiente es **V74**).

### Seguridad y permisos
- `SecurityConfig`: stateless, JWT. Públicos: `/api/auth/**`, `GET /api/promociones/activas`, `POST /api/cotizaciones/publica`, `GET /api/lotes/publico`, `PUT /api/lotes/publico/*/estado`, `POST /api/lotes/publico/verificar-asesor`, `GET|POST /api/forms-publico/**`, `GET /api/score-publico`. Cadena aparte para `/uploads/**` (cacheable, público).
- `SecurityConfig` deja pasar el despacho de errores (`DispatcherType.ERROR`): sin eso un 500 o un 400 salía como 401 "No autenticado" y el frontend cerraba sesión (así falló el login cuando un `Set.of(...).contains(null)` rompió las notificaciones). Un 401 ahora es siempre falta de autenticación real.
- `JwtAuthFilter` confía en el rol del token (no consulta BD). `CurrentUserProvider.getUsuarioActual()` sí consulta por email.
- Roles (`Role`): `ASESOR, LIDER_AREA` (en UI = "Administración"), `EQUIPO_INTERNO, ADMIN`.
- 15 módulos (`Modulo`): LEADS, PIPELINE, COTIZADOR, LOTES, PLANO, VENTAS, SCORE, CLIENTES, FINANZAS, GASTOS, CALENDARIO, ASESORES_EXTERNOS, COMUNIDADES, WE_FORMS, MATERIAL. `ModulosAcceso` define máximo y default por rol; `Usuario.modulos` (CSV, null = default del rol).
- `ModuloAccesoInterceptor`: mapa prefijo de API → módulos que lo habilitan (más específico primero). **Un endpoint nuevo de un módulo debe agregarse ahí.** APIs compartidas (desarrollos, usuarios, notificaciones, tareas, reportes) solo por rol.
- Cada servicio valida su rol con helpers tipo `exigirAdminOLider()` / `exigirAdmin(...)`. Acciones destructivas piden la contraseña de quien las hace (eliminar venta: admin y administración, con cuenta regresiva de 10 s en la UI; limpiar mapa: solo admin).
- Login: `AuthService` + `TurnstileService` (captcha Cloudflare, desactivado por defecto). PIN público: `AsesorPublicoService` + `LimitadorPinPublico` y `AsesorPublicoController` (5 fallos / 10 min por IP). La IP sale de `IpCliente.de(request)`: solo lee `X-Forwarded-For` si la conexión directa es loopback/red privada (el proxy) y toma la IP añadida por el proxy (de derecha a izquierda), no la primera, que el cliente puede inventar.
- Usuario de sistema `cotizador-publico@weinversiones.com` (V17) atribuye acciones sin sesión (cotizador público, apartado público, registros de venta).

### Dominio (servicios grandes — leerlos antes de tocar su área)
- **VentaService** (≈920 l.): ventas con varios lotes (`VentaLote`), aportaciones, copropietarios (hasta 4 + principal), recibos (`ReciboVenta` con líneas `PagoVenta` por `TipoAbono`: ENGANCHE, MENSUALIDAD, APORTACION, APARTADO). Recibos se **anulan**, no se borran (bitácora `ReciboVentaHistorial`). Número de venta consecutivo, manual o auto (mayor+1), con `bloquearNumeracion()` y recorrido de la racha; al eliminar, las mayores bajan 1. Contrato firmado (`registrarContrato`). `Venta.modalidadPago` (`ModalidadPago`: EFECTIVO o TRANSFERENCIA, opcional; distinto de `formaPago`, que es el esquema tipo "Sin enganche · 60 MSI"; V66) y `MedioFirma` del contrato (FISICO, DOCUSIGN o AMBOS). `Venta.numeroContrato` (opcional, único sin importar mayúsculas, índice parcial V65; se edita con `registrarNumeroContrato` desde el detalle de la venta y, por `PUT /api/clientes/ventas/{id}/numero-contrato`, desde el detalle del cliente). `crearDesdeRegistroDeVenta` → lotes en `EN_PROCESO_DE_FIRMA`, fecha provisional, `depositoPendiente` aplicable con `aplicarDeposito`. **El estado de los lotes lo manda la venta**: desde el panel (`crear`) quedan `EN_PROCESO_DE_FIRMA` sin contrato firmado y `VENDIDO` firmado (`LoteService.marcarPorVenta`; ya no existe la casilla `marcarLoteVendido`); `registrarContrato` los mueve solo si cambia la firma (`alinearLotesConContrato`: firmada → VENDIDO, sin firma → EN_PROCESO_DE_FIRMA salvo que otra venta firmada tenga el lote; corregir fecha, medio o enlace no los mueve); un lote no puede estar en dos ventas (`crearVenta` lo rechaza con 409; el índice de `venta_lote` solo lo impide dentro de la misma venta); `eliminar` siempre regresa a DISPONIBLE los lotes VENDIDO o EN_PROCESO_DE_FIRMA que ninguna otra venta tenga (ya no existe `liberarLotes`). Solo ADMIN/LIDER.
- **ComisionService** (≈730 l.): comisión 5% por defecto (máx 10%) por venta + una secundaria para copropietario. Devengos reconstruidos por completo desde los abonos en cada `sincronizar`. Regla nueva (`reglaNueva`): enganche cuenta completo, mensualidad/aportación la mitad, apartado 0; entrega el sábado siguiente al abono y solo con contrato firmado (`Totales.bloqueada`). Entregar crea un `Gasto` origen COMISION; devolver/anular entrega soportados. Las ventas viejas conservan la regla anterior (UNA_EXHIBICION / PARCIALIDADES). **Desglose** (`GET /api/finanzas/comisiones/desglose`, `ComisionDesgloseDto`; sección "Desglose de comisiones" bajo las tarjetas de Finanzas → Comisiones con vistas Composición [barra segmentada pagada / por pagar / retenida / por generar con corchete de la comisión generada y leyenda con monto, % y una línea de explicación; colores validados con la skill de dataviz, ver `CLASES_REPARTO` en `finanzas.component.ts`] / Por asesor / Por desarrollo): por comisión no cancelada, total = faltaPorGenerar + ganado; ganado = entregado + porEntregar + detenido (contrato sin firmar, `Totales.bloqueada`) − entregadoDeMas; porEntregar = retrasado + tocaSabado + masAdelante. Por asesor (clave `U-`/`E-`, `ComisionDto.asesorClave`) y por desarrollo ("Varios desarrollos" si la venta tiene lotes de dos; "Venta eliminada" si ya no existe). `por-entregar` trae, por comisión, `abonos` (fecha, concepto, monto del abono, `porcentaje` aplicado 100/50 —null en "Venta" de una exhibición—, `parcial` si solo completó la comisión, y aporte; `findAllConPagoOrdenados` carga el abono de cada devengo de una vez), `ganadoAlSabado` y `yaEntregado`; el frontend lo agrupa por asesor ("Pagos del sábado") y lo muestra en la tabla "Ver cálculo" (en celular, lista) con la nota de la regla (`reglaDe`). **Vocabulario de la UI** (pestaña Comisiones, tono formal pedido por el usuario; los nombres internos no cambian): devengado = "Comisión generada", entregado = "Pagada", porEntregar = "Por pagar" (retrasado = "Vencida", tocaSabado = "Programada dd/mm/aaaa", masAdelante = "Fechas posteriores"), detenido = "Retenida", faltaPorGenerar = "Por generar"; entregar = "Registrar pago"; ticket = "comprobante"; estados Por generar / En generación / Pago parcial / Pagada / Cancelada. El PDF del comprobante conserva sus textos. Una comisión **cancelada** no cuenta en nada: ni en Retrasadas, ni en la lista del sábado, ni se puede entregar (409); al reactivarla vuelve a contar.
- **LoteService** (≈630 l.): estados `DISPONIBLE, APARTADO, APARTADO_A_PLAZO, APARTADO_CON_DINERO, EN_PROCESO_DE_FIRMA, RESERVADO_WE, VENDIDO`. Los 5 últimos solo los mueve ADMIN/LIDER (con nota obligatoria). **`RESERVADO_WE` ("Reservado por We")**: lote que la empresa se guarda; solo ADMIN/LIDER lo ven así, para todos los demás y sin sesión (planos públicos, cotizador) sale como `VENDIDO`. Se disfraza en el servidor, no en el navegador: `model/VisibilidadLote` decide por el rol de la petición (`SecurityContextHolder`) y lo aplican `LoteDto.from`, `MovimientoLoteDto.from` (el movimiento disfrazado sale sin nota, asesor, cliente, monto ni usuario), `resumenPorDesarrollo` (para el resto suma a VENDIDO y quita la clave) y los filtros de `buscarPaginado` (para el resto, VENDIDO incluye los reservados). **Todo DTO nuevo que muestre un estado de lote debe pasar por `VisibilidadLote.visible`.** Los endpoints públicos `/api/lotes/publico/**` usan `LoteDto.paraPublico` (`VisibilidadLote.comoPublico`), que ignora el rol aunque la petición traiga el token de un admin; además el interceptor de auth del frontend ni manda el token a esa ruta, y el prefetch de `index.html` va sin sesión: los links públicos se ven igual para todos. Aparte sigue existiendo el "reservado" derivado: un VENDIDO sin ninguna `VentaLote` (`sinVentaRegistrada`, solo lo reciben ADMIN/LIDER); `reservadosWe` del resumen y el filtro `RESERVADO_WE` suman ambos. En el frontend, `ESTADOS_LOTE_ORDEN` (los 6 de siempre) es para leyendas y filtros de cualquiera y `ESTADOS_LOTE_ORDEN_ADMIN` (con `RESERVADO_WE`) para admin/administración. Todo cambio pasa por `cambiarEstadoConHistorial` → `MovimientoLote`. `MovimientoLoteDto.viaPublico` marca lo hecho sin sesión (usuario de sistema): ahí `nombreAsesor` es quien lo hizo; en un cambio del panel es el asesor al que se le apartó (el historial lo muestra como "para …" debajo de quién lo hizo). Versión pública `cambiarEstadoPublico` (sin estados restringidos, no libera `APARTADO`). `LoteAutoLiberacionScheduler` (cada 5 min) libera vencidos. **Lote con venta** (`validarContraVenta`, dentro de `cambiarEstado`): si está VENDIDO o EN_PROCESO_DE_FIRMA no se cambia a mano (409; para liberarlo se elimina la venta) y si quedó en otro estado (datos de antes de la regla) solo puede volver a uno de esos dos; un lote sin venta no pasa a mano a VENDIDO ni EN_PROCESO_DE_FIRMA (400: se registra la venta; en Lotes y Plano elegirlos abre Nueva venta con `?desarrolloId&loteId`). `cambiarEstadoPublico` y el liberador automático no tocan lotes con venta. `LoteDto.ventaNumero` (solo ADMIN/LIDER, lo pone `marcarVentas` en buscar, mapa y lo que devuelve un cambio) alimenta el chip "Venta #N" y `estadosParaAdmin` del frontend (`core/models/lote.model.ts`). Plano: polígonos en JSON (`PoligonoMapaJson`), imagen en `UPLOADS_DIR`.
- **FinanzasService**: valor vendido por desarrollo/lote y calendario de ingresos esperado vs recibido (libro con contra-asientos de recibos anulados y devoluciones de comisión); `cobroPorVenta()` calcula atrasos (también de contado) para Comisiones. Carga todo en memoria por llamada.
- **CalendarioPagos** (clase estática, la ÚNICA regla de "qué le toca pagar al cliente y cuándo"; la usan Finanzas, Comisiones, Clientes y la tabla de amortización, así los números coinciden): `conceptos(venta, precio, aportaciones)` = enganche/pago inicial (solo si la etiqueta es "Enganche" o "Pago inicial"; "Aportación anual" de ventas viejas no se proyecta) el día de la venta, una mensualidad por mes del plazo en su `diaPago` (último día si el mes es corto; arranca el mes de la venta o el siguiente), aportaciones en su mes (reemplazan la mensualidad y llevan su N.º; fuera del plazo van sin número), contado = todo el precio el día de la venta; nunca pasa del precio y si faltan ≤ $1 (redondeo de la mensualidad) los absorbe la última mensualidad. `estadoDeCuenta(conceptos, precio, abonado, hoy)`: lo abonado (recibos vigentes; el `depositoPendiente` de un registro de venta no cuenta hasta aplicarlo, decisión del usuario) cubre del pago más antiguo al más nuevo; estados `EstadoPagoPlan` PAGADO / ATRASADO (desde el día siguiente a su fecha) / LE_TOCA (el siguiente sin cubrir, todos los de esa fecha) / PENDIENTE; tolerancia de 1 centavo; lo que el plan no fecha va en un renglón final "Sin fecha en el plan" que nunca vence. `pagosAtrasados` cuenta renglones atrasados y `mensualidadesAtrasadas` cuántos de ellos son mensualidades (el frontend dice "N mensualidades" si son iguales y "N pagos" si no: `frasePagosAtrasados`/`cuentaAtraso` en `core/models/amortizacion.model.ts`). **EstadoCuentaService** arma `AmortizacionDto` (titular con su número del desarrollo de la venta y teléfono, copropietarios, términos, resumen y filas): `GET /api/ventas/{id}/amortizacion` y `GET /api/clientes/{id}/amortizaciones` (titular o copropietario; admin y Administración). Frontend: `shared/tabla-amortizacion` (bloque plegable, caja con scroll y encabezados fijos que se coloca en el pago actual, botón PDF) y `PdfAmortizacionService` (diseño de la cotización: banda azul, datos del cliente/venta, resumen a la fecha, tabla autoTable, pie con página).
- **LeadService / SeguimientoService / EtiquetaService / ColumnaPersonalizadaService**: leads por asesor (admin ve todos), "fríos" tras 15 días, archivar, reasignar, importar Excel por fila, etiquetas y columnas del pipeline privadas por asesor.
- **ClienteService**: ficha con `paisResidencia` (validado contra `model/Paises` + `resources/paises.txt`; la misma lista está en `frontend/src/app/core/data/paises.ts`, editar ambas) y `estado` (si el país es México debe ser uno de los 32 de `model/EstadosMexico` + `resources/estados-mx.txt`, espejo en `core/data/estados-mx.ts`; con otro país, texto libre) y número consecutivo editable (`cambiarNumero`), validación CURP/RFC, anti-duplicado (CURP / nombre+nacimiento / teléfono → `ClienteDuplicadoException`), `resolverDesdeRegistroDeVenta` (vincula por CURP, nunca por nombre). Al arrancar migra ventas viejas a clientes. Lista, ficha y cada compra traen el atraso (`atrasoMonto`, `pagosAtrasados`, `mensualidadesAtrasadas`, `atrasadoDesde`, próximo pago) calculado con `CalendarioPagos` en `Resumenes`, sumando también las ventas donde es copropietario; la lista tiene el filtro "Con pagos atrasados" y la ficha la tarjeta "Pagos atrasados", la columna Estado en Compras y la sección "Tabla de amortización" (arranca abierta la primera compra atrasada o la más reciente). El detalle de la venta muestra el aviso de atraso y la tabla junto a la cobranza.
- **WeFormService / WeFormPublicoService**: formularios de registro de venta tipo Google Forms (preguntas con `DestinoPregunta` que mapean a cliente/venta). Envío público con PIN: valida, crea cliente + venta + respuesta en una transacción; archivos ≤2 MB (JPG/PNG/WEBP/PDF por firma) en carpeta privada. `forms-publico` va por slug. `POST /api/we-forms/{id}/duplicar` (`WeFormService.duplicar`) copia las preguntas activas a un formulario nuevo (Activo, link propio, sin respuestas) para el desarrollo elegido; botón "Duplicar" en la lista. Tipo de pregunta `PAIS` (selector con buscador `shared/lista-selector`, genérico para países y estados; la pregunta predefinida `ESTADO` pasa a lista de estados cuando el país elegido es México): la primera de cada formulario llena `Cliente.paisResidencia` (en cliente existente solo si está vacío).
- **MaterialService** (V67): material de venta (copys como texto y/o archivo JPG/PNG/WEBP/PDF/MP4 ≤ 25 MB validado por firma; categoría fija COPY/FLYER/BROCHURE/VIDEO/OTRO; `ProyectoMaterial` SAMAI/NANUU/AMBOS). Panel `/api/material` (módulo MATERIAL, multipart con campos de formulario + `archivo`; Administración y Admin). Plano público `/api/material-publico` (sin sesión, PIN en `X-Asesor-Pin` vía `LimitadorPinPublico`, igual que We Forms; los archivos viven en `UPLOADS_PRIVADOS_DIR/material` y solo se sirven por el endpoint, que el frontend baja como blob con la cabecera). Al subir un JPG/PNG se genera una miniatura (`material-{id}-mini.jpg`, 480 px, `GET …/{id}/miniatura`; webp sirve el original; PDF/MP4 sin miniatura). Frontend: `shared/material-miniatura` (carga perezosa) y `shared/material-visor` (imagen/video/PDF embebido con flechas), ambos reciben una función `cargar` que cambia entre panel (sesión) y plano público (PIN). El plano público abre `/material?proyecto=samai|nanuu` (`features/publico/material-publico`, pestaña nueva, grid de tarjetas; mismo patrón que `/we-forms`; título en `scripts/paginas-publicas.mjs`); el PIN que usa es el que guarda `WeFormsPublicoService`. Las tarjetas llevan `data-material-id`: `material-visor` anima (WAAPI, transform/opacity, con tope de tiempo por si el navegador no pinta cuadros) el zoom desde/hacia esa tarjeta. `multipart.max-file-size` subió a 25 MB (si hay nginx delante, `client_max_body_size` debe ser ≥ 26m). **Galerías** (V68, categoría `GALERIA`): sin archivo propio; tabla `material_imagen` (orden 0 = portada), hasta 25 imágenes JPG/PNG/WEBP ≤ 10 MB en `UPLOADS_PRIVADOS_DIR/material/galeria-{id}/imagen-{imagenId}.ext` (+ `-mini.jpg`). Se suben de a una (`POST /{id}/imagenes`), se quitan (`DELETE /{id}/imagenes/{imagenId}`) y se ordenan (`PUT /{id}/imagenes/orden`); imagen, miniatura y `GET /{id}/zip` existen en panel y público (el ZIP se escribe en streaming, sin armarlo en memoria). `MaterialDtos.Item.imagenes` las trae en orden. Frontend: `shared/material-galeria-mosaico` (portada de la tarjeta), `shared/imagen-diferida` (miniatura perezosa genérica) y el visor en modo galería (`imagenInicial`, `cargarImagen`, `cargarMiniaturaImagen`, tira de miniaturas, deslizar con el dedo).
- **GastoService / GastoRecurrenteService / TipoGastoService**: gastos con ticket privado (`UPLOADS_PRIVADOS_DIR`), recurrentes y nómina semanal (sábados) por usuario. Admin y Administración modifican (`PUT /api/gastos/{id}` multipart: concepto, fecha, monto, ticket, `quitarTicket`) y eliminan (`POST /api/gastos/{id}/eliminar` con la contraseña) egresos. Un egreso de origen COMISION se sincroniza con su entrega: editar monto/fecha llama `ComisionService.corregirEntregaDeGasto` (tope: lo ganado aún no entregado; recalcula `entregadoAcumulado` y los abonos del ticket de esa entrega y las posteriores) y eliminar llama `anularEntregaDeGasto`. El pago de un recurrente solo se borra con "Deshacer pago". `ModalidadPago` (EFECTIVO/TRANSFERENCIA/DEPOSITO) también es el tipo de `VentaComisionEntrega.formaPago`, pero el panel de comisiones solo ofrece efectivo y transferencia.
- **ComercializadoraService / ComercializadoraPublicoService** (V71): una comercializadora = nombre + líder (un asesor activo que no es LINEA, externo o interno —la ficha de comunidad de un usuario ASESOR, que el selector marca "(interno)" y `ComunidadInternosService` no deja quitar del árbol mientras lidere una—; si era INDEPENDIENTE pasa a LIDER; una comercializadora por líder, y no se puede cambiar de líder con integrantes) + `token` secreto (192 bits) del enlace `/unirse/:token` que la líder comparte. Panel `/api/comercializadoras` (mismo módulo que Asesores externos; ver `ModuloAccesoInterceptor`), pantalla `features/comercializadoras` (menú, debajo de Asesores externos) y sección "Altas de comercializadoras" en We Forms. Público `/api/comercializadoras-publico/{token}` (GET info, POST `/unirse`; sin sesión; 404 igual para token inválido o comercializadora inactiva; límite de 10 altas/hora por IP y 60 por enlace): crea un `AsesorExterno` LINEA nivel 1 con la líder de líder directo, contrato VIGENTE, acceso SAMAI y Nanuu, `traidoPorAsesor` = la líder, `comercializadora_id` (columna nueva en `asesor_externo`) y un PIN aleatorio de 4 caracteres (sin 0/O/1/I) que solo se muestra en la pantalla de bienvenida; rechaza un celular que ya tenga otro asesor activo. El formulario acepta un `pin` elegido por el integrante (opcional; vacío = al azar): `PinAsesor.validarElegido` no revela de quién es un PIN en uso y los PINs rechazados cuentan contra un tope (5/hora por IP) para que no sirva para averiguar qué PINs existen. Los PINs los genera/valida `PinAsesor` (compartido con la edición de integrantes). `PUT/DELETE /api/comercializadoras/{id}/integrantes/{asesorId}` corrigen nombre/celular/correo/PIN (pin null = igual, vacío = nuevo al azar) y quitan: sin historial se borra el `AsesorExterno`; con ventas, comisiones, clientes captados, registros de We Forms o siendo "traído por" de otro solo se desactiva (`activo=false`, el PIN deja de servir); con gente reportándole en Comunidades We responde 409. `Item.integrantes` cuenta solo activos, pero eliminar o cambiar de líder usa el total.
- **ScoreService** (módulo SCORE "Score de ventas"; `GET /api/score?desde&hasta`, pantalla `features/panel/score`, en el menú debajo de Ventas; Admin y Administración: V73 solo le AGREGÓ `SCORE` a la lista de módulos de los de Administración que ya existían): ranking de asesores internos y externos juntos (sin filtro ni etiqueta de tipo; el DTO conserva `tipo`) por número de ventas del módulo Ventas en el periodo (por fecha de venta; arranca en el mes en curso). Solo compiten asesores (usuarios con rol ASESOR y asesores externos): un usuario con otro rol no entra aunque sea el asesor de una venta (`ScoreService.participante`). Una venta compartida cuenta completa para el principal y para el copropietario que compitan (su comisión secundaria no cancelada; ver `VentaComisionRepository.findByVentaIdInAndSecundariaTrueAndCanceladaFalse`); los inactivos no aparecen pero sus ventas sí suman a `totalVentas`, que excluye las ventas sin ningún asesor (solo administradores); la ficha de comunidad de un interno suma en la fila de su usuario. Con las mismas ventas comparten lugar sin saltos (1, 2, 2, 3: lo numera `conPosiciones` en el frontend). Muestra ventas y lotes. **Versión pública** `/cotizador-publico/score` (mismo `ScoreComponent` con `data.publico`; sin portada: `CotizadorPublicoLayoutComponent.conPortada`; enlaces en la barra y en la portada): `GET /api/score-publico` (`ScorePublicoController`, `ScoreService.rankingPublico`) sin sesión ni PIN; si el dispositivo tiene el PIN guardado (`WeFormsPublicoService.pin`) lo manda en `X-Asesor-Pin` solo para marcar "Tú" (`miClave` vía `ScoreService.claveDe`); `LimitadorPinPublico.identificarSiViene` no lanza error, cuenta los PIN rechazados contra el mismo tope por IP y, al tope, ya no revisa; con `pinRechazado` la página olvida el PIN guardado. Debajo de la portada de `/cotizador-publico` (solo ahí, no en Lotes: `enCotizador` del layout) va `features/publico/score-resumen`: top 5 de todo el historial, enlace al score completo, "Tú" o "Tú (también) vas en el N.º lugar" con el PIN guardado; sin ventas no se muestra.
- **CotizacionService / PromocionService**, **AsesorExternoService** (contrato, jerarquía de equipos, ficha, PIN, acceso por proyecto samai/nanuu), **ComunidadInternosService**, **DesarrolloService** (catálogo y plano), **TareaService**, **EventoCalendarioService**, **ReporteService**, **UsuarioService** (CRUD, módulos, nómina, PIN).
- **Nombre "Registrar venta"** (antes "Precontrato"): lo que ve el usuario dice "Registrar venta"/"registro de venta". Se conservaron por estar guardados en la BD: el valor `FuenteCliente.PRECONTRATO`, los textos viejos de notas (`LoteService.NOTAS_REGISTRO_VENTA`) y la clave de aviso `PRECONTRATO_NUEVO` (`NotificacionService.TIPO_REGISTRO_VENTA_ANTERIOR`, también en `push_enviada`); no editar las migraciones V62/V64 aunque mencionen "precontrato" (cambiaría su checksum de Flyway).
- **NotificacionService**: notificaciones calculadas al vuelo (leads, tareas, eventos, lotes, ventas, respuestas We Forms); solo se guarda lo leído (`NotificacionLeida`). **Lotes desincronizados con Ventas** (`agregarAvisosDeLotesDesincronizados`, solo ADMIN y LIDER_AREA): un aviso por lote `LOTE_SIN_VENTA` (VENDIDO sin ninguna `VentaLote`, `LoteRepository.findVendidosSinVenta`; se sigue mostrando como "Reservado por We" a admin/Administración y como Vendido afuera, decisión del usuario) y `LOTE_VENTA_DESALINEADA` (lote en una venta que no está VENDIDO ni EN_PROCESO_DE_FIRMA, `VentaLoteRepository.findConLoteFueraDeEstadoDeVenta`). ## Pendientes / riesgos conocidos
1. `JWT_SECRET` nunca seteado en el VPS (usa el default de `application.properties`) — crítico. Rotar la password de DB que se pegó en un chat.
2. `PUT /api/lotes/publico/*/estado` no exige PIN en servidor (el PIN solo gatea la UI).
3. Token válido tras desactivar un usuario (480 min por defecto).
4. Varios servicios cargan tablas completas en memoria (`FinanzasService.Datos`, `ComisionService.Totales`, `ClienteService.verificarDuplicado`, `LoteService.actualizarPrecioManzana`).
5. Código marcado "temporal": `Venta.actualizar` y su botón; conviven dos reglas de comisión (`reglaNueva`).
6. `API_CONTRACT.md` solo cubre el login y no menciona `captchaToken`; `README.md` vacío.
